# Concitech AdSense 低价值内容修复设计

日期：2026-08-19

## 现状与根因

AdSense 审核的是页面对访问者的独立价值，不是页面数量或字数。当前主站只有首页、项目、关于、联系、隐私和编辑原则六个页面；主要内容是项目简介和通往子域的链接。用户无法在主域完成一次深入阅读，审核系统也容易把它识别为目录页或跳转入口。

线上还存在一个明确的抓取问题：Cloudflare 会把 `/projects.html` 以 308 重定向到 `/projects`，但页面 canonical 和 sitemap 仍声明带 `.html` 的旧地址。虽然这不会单独造成“低价值内容”，却会浪费抓取信号并让首选网址不一致。

## 方案比较

1. 只扩写现有页面：改动最小，但主站仍缺少可独立消费的内容，不能消除目录站特征。
2. 在主域新增原创开发笔记和案例：以真实代码、发布流程和已验证限制为依据，建立内容入口、相关文章和清晰内部导航；这是本轮采用方案。
3. 把 AI 日报迁到主域：内容规模最大，但会引入迁移、重定向、历史索引和自动发布风险，不适合作为本轮修复。

## 信息架构

- 首页：明确站点核心价值，并展示最新原创笔记，而不只是外部项目卡片。
- `/notes`：主域内容索引，说明每篇文章解决的问题、验证依据和更新时间。
- 三篇首发案例：分别解释 AI 日报的来源验证与双语发布、Tweet Craft 的复制降级设计、静态站的可抓取质量检查。内容只陈述仓库中能验证的事实。
- 项目页：从营销式功能列表改为“问题—设计取舍—限制—验证”摘要，并链接到对应深度文章。
- 信任页：保留作者、联系、隐私和编辑原则，但不加载广告脚本。

## 广告与抓取边界

- AdSense loader 只保留在首页、内容索引和原创文章页；不在联系、隐私、关于、编辑原则及纯项目目录页加载，降低自动广告出现在非内容页的风险。
- 所有 canonical、内部链接和 sitemap 统一为 Cloudflare 实际提供的无扩展名 URL。
- sitemap 只收录有明确用户价值、允许索引且返回 200 的页面；robots 继续允许正常抓取。
- 文章页输出 `Article` JSON-LD、作者、发布日期、修改日期和可核验的相关项目链接。

## 验证

- 自动检查每个索引页的 title、description、唯一 H1、canonical、内部链接和结构化数据。
- 检查 sitemap URL 与 canonical 一致，不再包含会 308 的 `.html` 地址。
- 浏览器分别以桌面和移动视口检查导航、正文可读性、焦点状态、横向溢出和控制台错误。
- 上线后逐页检查 HTTP 状态、canonical、sitemap、robots 与 ads.txt，再请求 AdSense 复审。
